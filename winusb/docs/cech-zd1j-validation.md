# CECH-ZD1J 検証記録

この文書は移植過程の検証記録。個体IDは`DEVICE_A`・`DEVICE_B`に置き換え、
試験用の録画TSと実行ログはリポジトリに含めていない。現在の利用手順は
[通常ホストの統合手順](cech-zd1j-integration.md)を参照。

## 環境と対象

Windows amd64、Visual Studio 18 Communityにインストールされたv143 toolset、
Windows SDK、`Release-static|x64`、Python 3.11、FR30再生成にはGo 1.26.0を使用。
比較対象のcoaxとpx4_drvのコミットは `cech-zd1j-design.md` を参照。
この記録は2026-10-26時点の独立部品に対する結果である。

## 実機で読み取り確認した範囲

接続台数は1台。PnP ServiceはWINUSB、interface GUIDは
`{B8F4B677-E19A-4BEB-A60C-C0A7AC2D0F6B}`。

| 項目 | 読み取り結果 |
|---|---|
| VID/PID | `054C:04B2` |
| USB serial descriptor index | 0（シリアル文字列なし） |
| interface / alternate | 0 / 0 |
| endpoint 0x81 | bulk、最大512バイト |
| endpoint 0x02 | bulk、最大512バイト |
| endpoint 0x83 | interrupt、最大64バイト |
| endpoint 0x84 | bulk、最大512バイト |

最初のdescriptorプローブは0x83をbulkと仮定したため、形式確認が失敗した。
その取得結果を根拠にinterruptとして照合するよう修正した。
修正後の照合コードは、下記の実機起動・識別試験で成功した。
descriptor確認時にvendor要求・reset・選局は実行しておらず、終了後にUSBハンドルを解放済み。

## 実機の起動・I2C識別試験

BonDriverCoax/coax関連アプリをすべて終了済みとの確認と実機試験の許可を得て、
接続中の1台へ以下を実行した。診断予算30,000msはこの試験の上限で、製品既定値ではない。

```text
torne_usb_probe.exe --initialize --timeout-ms 30000
torne_usb_probe.exe --identify --timeout-ms 30000
```

| 項目 | 実測結果 |
|---|---|
| 初回C++ MB86H47起動 | result=0、memory_result=0、OS error=0、62ms |
| 識別試験時の再起動 | result=0、memory_result=0、OS error=0、58ms |
| core1生存確認 | 成功。最終読取りアドレス `0x17A3F7C` |
| DiB8096電源・reset | result=0、OS error=0 |
| I2C列挙 | アドレス0x12、レジスター1287へ3、result=0 |
| 復調器vendor ID | `0x01B3` |
| 復調器device ID | `0x8002`（元実装が認識するDiB8000C識別値） |
| I2C識別 | result=0、recognized=1、OS error=0 |

この結果は2回の診断実行に限る。長時間・多数回・複数台の起動成功率を示すものではない。
`--identify` は復調器の全初期化、チューナー較正、選局を実行していない。
各プローブ終了時にWinUSB/file/eventハンドルを解放している。

利用者から申告された受信可能な物理チャンネルは13、14、15、18、19、20、29、30。
以下の追加診断で全8チャンネルのロックと最初のTSを確認した。

## 全初期化・選局・最初のTS（2026-10-26）

復調器は元coaxのGo実装を別プロセスの診断helperとして使用し、C++側が
WinUSB、同期mailbox I2C、MB86H47起動、TSエンジンと読み出しを所有する。
これは比較用構成であり、DriverHostへの統合や復調器のC++移植完了を意味しない。

アンテナ接続確認前は13～20の一部でロックした一方、29・30は5秒待っても
ロックせず、その後13も失敗した。元coaxのUSB経路でも13・29・30が失敗した。
USB再接続後、利用者がアンテナケーブルを接続し直してから、次の順で試験した。
両方の条件を変えているため、原因をアンテナだけに確定することはできない。

1. 元coaxのUSB/I2C/TS経路：13・29・30すべてロック、TS受信成功。
   初回TSまで31/25/26ms、それぞれ62980/63168/63168バイト。
2. 追加実装：13・29・30すべてロック、最初のTS受信成功。
3. 追加実装の連続選局：13,14,15,18,19,20,29,30,13,29,30の11回すべて成功。

最後の試験は `--receive --timeout-ms 60000 --channels 13,14,15,18,19,20,29,30,13,29,30`。
MB86H47起動59ms、復調器全初期化149ms、初回選局2711ms、以後1356～1787ms。
各選局後6144バイトを読み、192バイト形式から188バイトTSを31パケット取得した。
最初のTSまで2～3ms、取得分のTEIは0、stopも全回成功した。
同期取得前の端数破棄は15～159バイトであり、連続受信のドロップ測定ではない。
ログ：ワークスペース直下 `torne-original-bridge-compare.log` と `torne-first-ts-amd64.log`。

各回で最初のTSを取得して停止する短時間試験であり、映像表示、サービスID、
CC連続性、長時間品質や、元の「まれにTSが来ない」問題の解消を証明しない。
試験終了後は復調器sleepとUSBハンドル解放を実行した。

追加の非実機試験ではTSエンジンのprepare/start/stop、EP reset未完了、
各prepare転送の失敗注入、旧generation拒否、およびhelper IPCの期限・取消を確認した。
元の復調器テスト、helperプロトコルテストとamd64の既存・追加ビルドも成功した。

## 有限時間の連続受信

診断へ`--duration-ms`を追加し、出力vectorをreadごとに解放・再利用しながら
逐次OVERLAPPED readを継続する。受信区間の終端ではreadを取消・回収して正常停止する。
操作全体の期限で指定受信時間が不足した場合は失敗とする。

| 条件 | TSパケット | TEI / CC異常 / 不正ヘッダー | 最大read間隔 |
|---|---:|---|---:|
| 13、10秒 | 114815 | 0 / 0 / 0 | 3ms |
| 29、10秒 | 141631 | 0 / 0 / 0 | 6ms |
| 30、10秒 | 141631 | 0 / 0 / 0 | 2ms |
| 13、60秒 | 688863 | 0 / 0 / 0 | 6ms |

60秒試験ログはワークスペース直下`torne-continuous-60s-amd64.log`。
CC異常は同じCCの再送も含む診断値で、USBドロップと同義ではない。
上記はLED制御追加前の試験。元coaxはチューナーOpenでDiB8096 GPIO 1をHigh、
ReleaseでLowにするが、最初の診断はこの表示操作を省略していた。
利用者の緑のままという指摘を受け、診断helperも全初期化後High、sleep前Lowを実行する。
GPIO要求の成功と実際のランプ色の目視確認は分けて評価する。
追加後の13チャンネル30秒受信では、利用者が赤への変化を目視確認した。
344447パケット、TEI/CC異常/不正ヘッダー各0、最大read間隔4ms、stopとsleep成功。
ログは`torne-led-continuous-amd64.log`。終了後の緑への復帰は目視未確認。
60秒試験の実行中に再リンクを試みたビルドはLNK1168で失敗した。
試験終了後の再ビルドは成功し、受信プロセスを強制終了してはいない。

## ReceiverBase・共有受信バッファ経由の診断

`torne_usb_probe --receiver --timeout-ms 60000 --channels 13,14,15,18,19,20,29,30,13 --duration-ms 2000`
を実機1台で実行した。通常のDriverHostへの登録ではなく、初期化済みのUSBと復調器helperを
借りる診断アダプターを使い、未Openでのcapture拒否、Open、選局前のcapture予約、
SetParameters(kHz)、ReceiverBase::Tune、188バイト単位のStreamBuffer::Write、
別スレッドのHandleRead、受信中からの選局、停止、Close後の拒否とCloseの冪等性を確認した。

9回すべて選局・最初のTS取得・停止に成功。各2秒の観測区間のTEI/CC異常/不正ヘッダーは0。
前のチャンネルを診断用に再開した短区間も含め、総投入218800パケットと
総読出し218800パケットが一致した。入力ごとの同期0x47と188バイト長も確認した。
選局ごとの読出し差分は、前の短区間の残りも読み得るため、総数の照合へ変更した。
この試験だけでサービスIDや旧チャンネルTSの完全排除を証明したとはしない。
ログは`torne-receiver-integration-amd64.log`。

アダプターは既存PX系から未参照。製品用の状態監視/統計、操作別期限、抜去対応、
復旧状態機械、非同期機種登録、BonDriver経由の検証は残る。

## 無TSの注入と明示的再選局

`--receiver-recovery --timeout-ms 30000 --channels 13,29,30,13 --duration-ms 1000`
で、最初の選局だけ復調器出力をHigh-Zにして無TSを作る診断を追加した。
初期の診断はTS待ち失敗後もReceiverBaseのCheckLock pollからStartを再実行してしまい、
診断用High-Z解除後のTSを取得した。このため期待した無TS失敗を確認できなかった。
少量TSを残留データと疑ったが、暗黙の再試行によるものと分かり、その仮説に基づく
パケット数/100ms待機の追加条件は取り除いた。

修正は追加アダプターだけに限定し、capture失敗を保持して既存の`-ECANCELED`
停止条件でpollを終了する。次の明示的SetFrequencyでのみ失敗状態を解除する。
エラー名の製品用整理と操作別deadline hookは本統合前に残る。
修正後はロック後のTSが0パケットのままTS待ち2秒でreadを取消・回収し、workerをjoin、
TSエンジン停止を完了した。選局開始を含む経過時間は約4.51～4.65秒だった。
その後の明示的な13→29→30→13選局は受信・停止に成功し、取得区間のTEI/CC異常/不正ヘッダーは0。
ログは`torne-receiver-no-ts-recovery-amd64.log`。
自然発生する元coaxの無受信問題を再現・修正した証明ではなく、High-Z注入条件の結果である。

### アンテナ調整後の2台同時再試験（2026-10-27）

利用者がアンテナ線を調整した後、auto設定の2クライアントを同時起動し、
一方を29→30、もう一方を30→29として各区間20秒受信した。
両個体IDの別割り当てをhostログで確認。4区間ともBonDriver出口281600パケット、
同期/TEI/CC異常/不正ヘッダー/読み取り失敗0、毎秒の状態取得19回。
USB直後も全区間raw_cc/TEI/raw_malformed 0だった。両クライアントは正常Close。
ログは`torne-bon-dual-adjusted-20261027-015129/`。
この条件で以前の29/30の異常は再現しなかった。アンテナ調整との関連を示すが、
厳密な減衰測定や変更前への戻し比較ではなく、原因確定・長期安定性の証明ではない。

続けて`torne-bon-dual-endurance-20261027-015331/`で、2台同時に29/30を交互に
各60秒×4区間受信した。全8区間それぞれ847872パケット、毎秒状態取得59回、
