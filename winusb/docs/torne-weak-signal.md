# torneのログと低ビットレート受信

対象はWindows WinUSB版のCECH-ZD1J。BonDriverの配布名は`BonDriver_Torne.dll`と
`BonDriver_Torne.ini`、ホストは`DriverHost_PX4.exe`と`DriverHost_PX4.ini`。
以前の`BonDriver_CECH-ZD1J.dll`を使う設定から切り替える場合、TVTest/EDCB側でもDLLを選び直す。

## ログ

`BonDriver_Torne.ini`の`[BonDriver]`に`DebugLog=false`を指定すると、BonDriverのログファイルを
作成しない。診断時は`true`で同名の`.log`を作成できる。設定省略時の既存PX系は従来の出力を維持。
ホストのログは別設定で、`[DriverHost_PX4]`の`DebugLog`に従う。
過去に作成済みのログファイルの削除は利用者の判断に任せる。

## TSが少ない局での待ち時間

2026-10-27の2台試験では、弱い13・14chのTSはPCRから約0.416Mbps、正常な41chは約17.27Mbps。
弱い局ではワンセグ相当のH.264/AACを持つPMT（PID 0x1FC8）を確認した。
正常局のMPEG-2映像PIDはこの弱い局の受信TSには見つからなかった。

旧設定の1024パケット単位では、選局自体が終わっても固定長バッファの充填とPurge後の破棄で
さらに約5秒待つ場合があり、6秒の計測区間にTSが届かない例もあった。
同じバイナリーで128パケット単位へ変えると、両個体で選局後約689～805msでTSが届いた。
これはチューナー初期化・選局時間を含まない。プローブは選局直後にPurgeしてから計測している。

以下は低ビットレート時の待ちを短縮した過去の試験設定。現在の配布既定値とは異なる。
PX-MLTなどの既存配布設定には変更を加えていない。

```ini
[BonDriver]
NumberOfPacketsPerBuffer=128
MaximumNumberOfBuffers=512
MinimumNumberOfBuffers=32
DebugLog=false
```

## 未訂正パケットの出力

他の機種と同じく、復調器が出したTEI付きのパケットも捨てずにアプリケーションへ渡す。
torneの復調器は既定で誤りパケットを捨てるため、初期化時にこの動作を解除している。
以前の`OutputErrorPackets`設定は削除し、INIに残っていても読まれない。

初期化時にレジスター299のSMO error-discardを解除し、読戻しを確認する。入力データを復元したり、
ホストでnullパケットを生成したりする処理ではない。同期取得はTEIも許容し、誤同期を抑えるため
8個の192byte周期と有効AFCを確認する。

以下は`OutputErrorPackets`設定があった時点の測定。実機の13・14chでは、この設定により2台とも約17.268Mbpsで出力し、選局後7～18msで最初の
BonDriverバッファを受信した。ただし6秒の区間で約68,736～68,864パケット中、
67,080～67,204がTEI付きかつTS形式不正だった。良好な受信とは評価できず、TVTestでの
Eカウント表示、映像の復号・再生は利用者による確認が必要。正常41chは同じ設定でも
同期・TEI・形式・CC異常0を確認した。

破損パケットを含むプローブ結果はFAILのまま記録している。従来のプローブは形式検査後にTEIを
数えるため、形式不正を伴うTEIはその欄に含まれない。上記TEI数は保存TSのヘッダーを別途解析した値。

最終の通常モードではx86/x64とも2台で41・42・47・49chを受信し、17・21・26chの無信号判定と
正常局への復帰を確認した。`channel_switch_stress`は各ビット数で2台を同時に4周期ずつ実行し、
各クライアント92,032パケット、選局失敗・空受信・同期・TEI・CC異常は0。
x86ではカードAPDUを35秒間重ね、105回成功・失敗0、最大応答2,637ms。
未訂正出力モードはx86ホストで2台を比較した結果で、x64での同モードの実機確認は対象外。
TVTestの映像・E表示と長時間運用は、この新版では別途確認が必要。

参考: [Linux dib8000.cの出力設定とSMO既定値](https://code.googlesource.com/linux/torvalds/linux/+/95940a04bfe8a4d246f4ca17c6a3b00148bdead0/drivers/media/dvb-frontends/dib8000.c)。
レジスター切替の効果と既存動作への復帰はCECH-ZD1J実機の保存TSで比較した。

## 弱い局・強すぎる局の選局失敗への対策

[aki0429/coax](https://github.com/aki0429/coax)の`docs/boards/cech-zd1j-stability.md`で、
DiB8096の探索ステップ間隔10msでは一部の局が`no_lock`になり、100msと再探索で受信できたと報告されている。
このリポジトリの復調器コードは同じ上流コミット`2d9f2c26`の移植のため、同じ変更を適用した。

- 探索ステップの最小間隔を10msから100msへ戻した。
- 探索が失敗またはロックしなかった場合、チャンネルのプロパティキャッシュを消して最大3回まで再探索する。
  全試行は1つの絶対期限を共有し、残りが1秒未満なら再探索しない。I2C/USBの通信エラーは再試行しない。
- 再探索のぶん、DriverHost側の選局予算を5秒から8秒へ延ばした。
- 従来常に有効だった高速選局（3ms間隔のポーリング、前回値・captrimの再利用）を見直した。
  前回値とcaptrimの再利用は、2回目以降の選局が約2.4秒から1.2～1.4秒になり、合わなければすぐ通常の探索へ戻ることを
  ブースターなしの環境の4台で確認したため、常に有効にした。以前の`RememberChannelParameters`、`ReuseCaptrim`設定は削除した。
- 3ms間隔のポーリング、温度補償の再利用、DC補正の短縮、同期前のデータ出力をまとめた`FastTuning`は、
  弱い局と強すぎる局で探索に失敗しやすく、前回値とcaptrimの再利用で2回目以降の選局が1.2～1.4秒になったため削除した。
  INIに残っていても読まれない。

選局は従来より遅くなる。受信できない電波を受信可能にする変更ではない。この組み合わせの実機確認は別途必要。

## 空きチャンネルの判定

探索に失敗した直後にr526とr533を読み、r526が50未満かつr533が0なら地デジの信号が無いと判断し、残りの再探索を省く。
ブースターなしの環境でUHF全域を走査した実測では、空きチャンネルはすべてr526=19・r533=0で、遠方の弱い局を含め信号があればr526は100以上だった。
空きチャンネルのスキャンは1チャンネルあたり約3秒から約1.1秒になった。

ただし、チューナーを開いた直後の最初の選局では、2回目以降はC/N 10dBで受信できる遠方局（強度-87dBm）が、1回だけr526=19・強度-109dBmを返した。
このため、初期化とスリープ後の最初の選局では判定を記録するだけで、再探索は省かない。

この判定は`DriverHost_PX4.ini`の`SkipEmptyChannels=true`で有効になる。既定の`false`では、すべてのチャンネルを最大3回探索する。
判定はチャンネルスキャンだけでなく録画の選局にも働き、基準を確認できた受信環境がブースターなしの1か所に限られるため、
取りこぼしを避ける`false`を既定にした。


## 低スペックPCでのDrop対策

TS受信スレッドは6144byteのbulk転送を1本だけ投入し、完了のたびに再投入していた。
通常優先度のため、ブラウザーなどの負荷で再投入が遅れると、その間bridgeの出力先がなくFIFOが溢れる。
また、DriverHost内の受信バッファが満杯になると受信スレッド自体が停止していた。

- 転送を複数（既定16本）同時に投入し、投入順に回収してTSの順序を保つ。
- 受信スレッドを他のPX系と同じ`THREAD_PRIORITY_TIME_CRITICAL`にした。
- 受信バッファが満杯の間は書けない分を捨てて受信を続け、件数を`buffer_full_dropped`としてログへ出す。
  他のPX系と同じ扱い。

```ini
[DeviceDefinition15.Config]
XferPackets=33
UrbMaxPackets=33
MaxUrbs=16
```

他の機種と同じ名前の設定で指定する。`UrbMaxPackets`（無ければ`XferPackets`）が1転送のTSパケット数、
`MaxUrbs`が同時投入数。torneのbulk転送は512バイトの倍数でないと途中で完了するため、
1転送の長さは`パケット数×188`を512の倍数へ切り下げる（33パケットで6144バイト、816パケットで153088バイト）。
上限は1MiB、同時投入数は1～64。
旧名の`UsbTransferSize`（バイト数）と`UsbTransferCount`は移行期間だけ読み、書かれていればそちらを優先する。

Dropが残る場合は`MaxUrbs`を増やす。他の機種と同じ`816 / 816 / 5`（153088バイト×5本）でも、ブースターなしの環境の4台同時受信でDropがないことを確認した。

## 現在の配布既定値（2026-10-28）

`BonDriver_Torne.ini`は1024パケット単位、最大64・最小4バッファ。
当時の`DriverHost_PX4.ini`のtorne専用設定は`OutputErrorPackets=true`（現在は設定を削除し、常にこの動作）。
この組み合わせでの実機再試験は未実施であり、上記の過去の測定結果をそのまま適用できない。
未訂正TSの出力は受信品質を改善する処理ではなく、アプリケーションに渡すパケットの扱いを変える。
